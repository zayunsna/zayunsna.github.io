# Why a 4-bit LLM can still run out of memory

“The weights fit” is not the same as “the request fits.” A 4-bit download mainly tells you about weight
storage. It does not tell you how much space the KV cache, temporary tensors, or inference runtime will need.

Two small experiments make the difference concrete. A packed matrix needs **0.5625 MiB**, including its
scales, but a deliberately simple implementation creates a **4 MiB** floating-point matrix to use it.
Separately, a real Qwen model's FP16 cache grows from **1.5 to 6 to 12 MiB** as the context and batch increase.
These are separate measurements, not components summed into a measured total for a quantized LLM.

## Start with what “4-bit” actually counts

For `N` weights, `N × 4 / 8` bytes is the ideal packed payload estimate, before metadata or byte alignment. It is not a process-memory
estimate. Formats may also store scales, zero points, higher-precision tensors and alignment padding.

The [downloadable experiment](/assets/code/int4_memory/memory_parts.py) packs two signed, symmetrically
quantized values into each byte. One FP32 scale is stored per group of 64 weights. This is an educational
NumPy implementation, **not** GPTQ, AWQ, GGUF or a production int4 kernel.

```python
import numpy as np
from memory_parts import pack_int4, unpack_int4

weight = np.random.default_rng(0).standard_normal((1024, 1024)).astype('float32')
packed, scale = pack_int4(weight)
restored = unpack_int4(packed, scale, weight.shape)
for name, array in [('original', weight), ('packed', packed),
                    ('scales', scale), ('restored', restored)]:
    print(name, array.nbytes)
```

Output:

```text
original 4194304
packed 524288
scales 65536
restored 4194304
```

The packed payload is 0.5 MiB; scales add 0.0625 MiB. The resulting 0.5625 MiB is about 7.1 times smaller
than the original FP32 array, not exactly eight times smaller. MiB here means `2**20` bytes.

The helper reconstructs an entire FP32 matrix before matrix multiplication. Its packed representation can
therefore coexist with a much larger temporary. A fused production kernel can avoid materializing the whole
matrix, so **this 4 MiB temporary is not a universal int4 overhead**. The lesson is to inspect the execution
path, not assume the on-disk representation is the peak working set. Array `.nbytes` also omits allocator
overhead and other intermediate arrays: it is payload accounting, not a peak-RSS measurement.

## The cache has its own precision

Weight quantization does not automatically quantize cached attention keys and values. Transformers exposes
quantized caches as a [separate cache strategy](https://huggingface.co/docs/transformers/kv_cache), with its
own backend and compatibility choices (checked 2026-11-01).

For a conventional full-attention cache with a uniform layer layout:

```text
KV bytes = 2 × layers × batch × cached tokens × KV heads × head dimension × bytes per element
```

Use **KV heads**, not necessarily query heads. The pinned
[Qwen2.5-0.5B-Instruct configuration](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/7ae557604adf67be50417f59c2c2f167def9a775/config.json)
has 24 layers, two KV heads and head dimension 64; its 14 query heads share the KV heads.
At FP16, that is `2 × 24 × 2 × 64 × 2 = 12,288` bytes per cached token per sequence.

I loaded the actual base transformer from that checkpoint and counted every cache key/value tensor after
forward passes, using repeated token ID 42 solely to control tensor shape. This is **CPU, FP16, eager
attention with FP16 weights**, not a test of a fully int4 model. No text-quality conclusion follows from
these inputs. The model is [Apache-2.0 licensed](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct).

| Batch | Cached tokens per sequence | Measured KV tensor payload | Formula agrees? |
|---:|---:|---:|---|
| 1 | 128 | 1,572,864 bytes / 1.5 MiB | Yes |
| 1 | 512 | 6,291,456 bytes / 6 MiB | Yes |
| 2 | 512 | 12,582,912 bytes / 12 MiB | Yes |

At batch 8 and 32,768 cached tokens per sequence, the **formula projects 3 GiB of FP16 KV payload alone**
for this configuration. I did not allocate that cache or deliberately cause an out-of-memory crash.
The projection excludes weights, activations, attention intermediates, padding and allocator/runtime costs.
Paged allocation, cache sharing, sliding windows, offloading and cache quantization can change the accounting.

## Run the bounded checks

Download [memory_parts.py](/assets/code/int4_memory/memory_parts.py) into an empty working folder.
With Python 3.12, install the [tested dependencies](/assets/code/int4_memory/requirements.txt):

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install torch==2.15.0 numpy==2.5.4 transformers==5.17.0
python memory_parts.py --output memory.json
```

The first run downloads the pinned public checkpoint; no API key or paid inference service is needed.
With the checkpoint already cached, `--local-files-only` prevents a download. The script runs only the
three bounded shapes above, checks FP16 cache dtypes and asserts exact agreement with the byte formula.
The standalone script and the code block above were both executed on 2026-11-01 with Python 3.12.13,
NumPy 2.5.4, PyTorch 2.15.0 and Transformers 5.17.0 on an Apple M5 Mac with 16 GiB unified memory.
The cache experiment ran on CPU, not MPS or CUDA. Saved evidence: [memory.json](/assets/code/int4_memory/memory.json).

## Diagnose the request that fails

If loading succeeds but a long prompt fails, try fewer total prompt-plus-generated tokens while keeping
the batch fixed. If single requests fit but concurrent requests fail, reduce simultaneous sequences.
These are different pressure points from the weight file itself. A failure during prefill may involve
attention intermediates; a failure as generation progresses may involve the growing cache. Neither symptom
alone proves the cause—measure at those stages using the chosen runtime's tools.

For an Apple Silicon machine, do not count system RAM and GPU memory as two independent physical budgets.
Apple describes CPU/GPU [shared resources in its unified-memory architecture](https://developer.apple.com/videos/play/tech-talks/10580/)
(checked 2026-11-01). This machine's 16 GiB is shared with the OS and other applications, not all available to the model.
Reducing safety limits is not a substitute for a memory budget.

The earlier [KV cache experiment](/tips/2026-10-20-kv_cache_memoization/) measures the speed it saves.
Here the practical question is different: after shrinking the weights, how much room is left for the
request? Budget the weights, cache and runtime separately, and leave headroom instead of treating the
4-bit file size as the answer.
