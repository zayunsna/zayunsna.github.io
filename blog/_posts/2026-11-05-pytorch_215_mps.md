# PyTorch 2.15 on Apple Silicon: is inference faster?

For one small FP32 network on an Apple M5, PyTorch 2.15 was modestly faster at batch 1; at batch 64,
the observed process ranges overlapped. That is enough to justify testing an upgrade on your workload,
not enough to promise a general Apple Silicon speedup.

Across three fresh processes per version, the median warmed forward took **0.389 ms on 2.14.0 and
0.336 ms on 2.15.0** at batch 1. At batch 64, the corresponding times were **0.457 and 0.449 ms**.
These are synchronized forward-call times, including Python and synchronization overhead, not pure GPU
kernel timings or end-to-end LLM throughput.

## What changed, and what this test does not cover

As of 2026-11-01, the official [PyTorch 2.15 announcement](https://pytorch.org/blog/pytorch-2-15-release-blog/),
dated October 28, describes additional native MPS kernels, a single-row `F.linear` decode path and FP8 support.
Its MoE decode results concern a different workload and machine. They are not measurements from this Mac.

This test uses ordinary dense layers at FP32. It does **not** exercise FP8, grouped MoE multiplication,
`torch.compile`, attention or a full trained language model. A speedup reported for a particular kernel does
not imply the same improvement for every model built on MPS.

## Hold the network fixed

The network has three linear layers: `1024 → 2048 → 1024 → 512`, with GELU after the first two. Its
4,722,176 parameters are untrained; the aim is inference timing and numerical agreement, not accuracy.
NumPy generates the same FP32 weights and 64-row input in both environments. The script hashes all weight,
bias and input bytes and asserts each full MPS output is close to its CPU reference.

_Tested 2026-11-01 on an Apple M5 Mac, 10 CPU cores, 16 GiB unified memory, macOS 27.0.1 arm64,
Python 3.12.13, NumPy 2.5.4, PyTorch 2.14.0 versus 2.15.0. MPS was available; CPU fallback was not used.
Both versions used `.eval()`, `torch.inference_mode()`, FP32 and one CPU thread. Other desktop applications
were not isolated, so treat the small differences as observations, not a controlled laboratory estimate._

Download [mps_benchmark.py](/assets/code/pytorch_215_mps/mps_benchmark.py), then create two environments:

```bash
uv venv -p 3.12 .venv214
uv venv -p 3.12 .venv215
uv pip install --python .venv214/bin/python torch==2.14.0 numpy==2.5.4
uv pip install --python .venv215/bin/python torch==2.15.0 numpy==2.5.4
.venv214/bin/python mps_benchmark.py --output run_1_214.json
.venv215/bin/python mps_benchmark.py --output run_2_215.json
```

For the reported comparison, I ran six processes **sequentially**, in the order `2.14, 2.15, 2.15, 2.14,
2.14, 2.15`. No other experiment from this coordinator ran alongside that final sequence. The downloadable
[run instructions](/assets/code/pytorch_215_mps/README.txt) describe the fixture and measurements.

Each process measures the first forward for a shape, warms it with 20 calls, then records 21 windows of
20 forwards each. Every forward is synchronized. This is the timing boundary used in the full script:

```python
import time
import torch

def timed_forward(model, x, repeats):
    torch.mps.synchronize()
    start = time.perf_counter()
    for _ in range(repeats):
        result = model(x)
        torch.mps.synchronize()
    return result, 1000 * (time.perf_counter() - start) / repeats
```

Without synchronization, a host timer can mostly measure queued work rather than completed GPU work.
[`torch.mps.synchronize()`](https://docs.pytorch.org/docs/2.15/generated/torch.mps.synchronize.html)
waits for MPS kernels to finish (checked 2026-11-01). Synchronizing every call is deliberate here: it also
adds overhead and does not represent a server pipelining many asynchronous requests.

## Warm results: do not hide the range

Within each process, I take the median of the 21 window means. The table then reports the median and range
of those **three process-level medians**, not a percentile over individual requests.

| Batch | 2.14.0 median | 2.14.0 process range | 2.15.0 median | 2.15.0 process range |
|---:|---:|---:|---:|---:|
| 1 | 0.389 ms | 0.347–0.433 ms | 0.336 ms | 0.328–0.346 ms |
| 64 | 0.457 ms | 0.445–0.470 ms | 0.449 ms | 0.443–0.468 ms |

The batch-1 ratio is about 1.16×, or 14% less elapsed time using the unrounded medians. At batch 64,
the roughly 2% reduction is small relative to the observed variation. Three processes on one laptop cannot
establish a general performance guarantee. The bars and whiskers in the cover show the same measurements;
the whiskers are observed ranges, **not confidence intervals**.

All six fixture hashes matched. Full output comparisons to the respective CPU reference passed at
`atol=2e-5, rtol=2e-4`; the saved JSON records each maximum absolute error. This checks the timing fixture,
not trained-model accuracy or compatibility with an existing application.

## A first forward is a different measurement

| Shape, in process order for that version | 2.14.0 first-forward times | 2.15.0 first-forward times |
|---|---|---|
| Batch 1 | 242.1, 51.9, 50.2 ms | 308.9, 71.9, 53.3 ms |
| Batch 64 | 4.4, 2.7, 2.6 ms | 7.5, 7.5, 7.5 ms |

These are fresh-**process** first forwards, not guaranteed cold OS/Metal shader caches. I did not clear
those caches or reboot between versions. Batch 64 is first for that shape but follows the batch-1 experiment
in the same process. Input construction, CPU reference calculation and device upload happen beforehand
and are recorded separately as `setup_ms`; imports and process startup are not included.

That distinction matters for short scripts. A fraction of a millisecond saved after warming does not tell
you whether a one-shot program becomes faster. Here the first-forward observations do not support calling
2.15 a startup improvement.

For your upgrade, keep the current environment, reproduce a representative input in a second environment,
check outputs, and measure both first-use and sustained behavior. Match the batch size, dtype and execution
mode you actually deploy. If the workload uses the new FP8 or MoE paths, test those explicitly rather than
borrowing this dense-network result.
